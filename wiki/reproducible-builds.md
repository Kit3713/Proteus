Proteus reduces every fingerprint the local OS can control on join and transmit, which makes it a security-relevant tool. The published binary has to be auditable: a user (or a security researcher, or a packaging maintainer) needs a path to confirm the artifact they downloaded was built from the public source on GitHub, with no third-party patches between source and bytes.

This page documents what "reproducible" means for Proteus, how to verify a downloaded binary, and the known sources of non-determinism that are intentionally tolerated.

## What "reproducible" means here

Given the same:

- Source tree at a specific git commit (the tag's commit)
- Pinned Rust toolchain (`rust-toolchain.toml`, currently `1.93.0`)
- Locked dependency tree (`Cargo.lock`, never regenerated by CI)
- `SOURCE_DATE_EPOCH` set to the tag commit's timestamp
- Build container (`fedora:43` for x86_64; `ubuntu-latest` host with the `gcc-aarch64-linux-gnu` cross-toolchain for aarch64)

`cargo build --release --frozen --locked` followed by `strip` produces a binary whose `sha256sum` matches the published `.sha256` artifact attached to the GitHub release.

This is "build reproducibility", not "from-source bootstrapping". You still trust the rustc binary you start with. If you want full bootstrap-style verification (compile rustc from source from the previous rustc, and so on), that is a deeper rabbit hole and out of scope for this project.

## Why pin the toolchain?

The default `rust-toolchain.toml` value used to be `channel = "stable"`. That floats: the binary built today on `stable` and the binary built next month on a newer `stable` can differ in the optimizer output even if the source is identical. For a tool that asks users to verify what they install, that floating channel is a hole.

Proteus pins to a specific `1.x.y` release. Bumping the pin is an intentional, reviewable change in `rust-toolchain.toml`, called out in `CHANGELOG.md`, and is expected to be re-verified before the next tag.

## Why `--frozen --locked`?

- `--locked` refuses to update `Cargo.lock` even if a transitive dep has a newer compatible version. The lockfile is the manifest of "what got built".
- `--frozen` refuses to even read the network — Cargo errors out instead of silently fetching a newer index.

Together they guarantee that what you build locally uses exactly the same dependency versions as the release runner.

## Why `SOURCE_DATE_EPOCH`?

A handful of build steps embed timestamps:

- The Rust compiler can embed a build timestamp in debug info; release builds with `strip = true` mostly remove this, but `SOURCE_DATE_EPOCH` makes it deterministic regardless.
- `rustc`, when generating `.rlib` archives, embeds modification times for member files. `SOURCE_DATE_EPOCH` sets a fixed epoch that the toolchain honors.
- Anything that calls `time()` during a build script picks up the same epoch.

Setting `SOURCE_DATE_EPOCH` to the tag commit's Unix timestamp removes wallclock-based variation between rebuilds. The release workflow does this automatically (`git log -1 --pretty=%ct` of the tagged commit).

## How to verify a downloaded binary

The fast path uses the script shipped in the repo:

```sh
git clone https://github.com/Kit3713/Proteus.git
cd Proteus
./scripts/verify-build.sh v0.4.0-beta1
```

`verify-build.sh`:

1. Clones the repo at the specified tag into a temporary directory.
2. Computes `SOURCE_DATE_EPOCH` from the tag commit's timestamp.
3. Runs `cargo build --release --frozen --locked` — Cargo will install the pinned toolchain via `rustup` if it is missing.
4. Strips the produced binary.
5. Fetches `proteus-x86_64-unknown-linux-gnu.sha256` from the matching GitHub release.
6. Prints both hashes and exits `0` (match), `1` (mismatch), or `2`/`3` (usage/build problem).

Manual recipe, if you prefer not to run the script:

```sh
TAG=v0.4.0-beta1
git clone --depth 1 --branch "$TAG" https://github.com/Kit3713/Proteus.git
cd Proteus
export SOURCE_DATE_EPOCH=$(git log -1 --pretty=%ct)
cargo build --release --frozen --locked
strip target/release/proteus

# Local hash
sha256sum target/release/proteus

# Published hash
curl -fsSL "https://github.com/Kit3713/Proteus/releases/download/${TAG}/proteus-x86_64-unknown-linux-gnu.sha256"

# diff them
```

## What's in the build-info file

Every release attaches `proteus-<arch>-unknown-linux-gnu.build-info` next to the binary. It is plain `key=value` text that records the exact environment the artifact was built in:

- `tag_commit_sha` — the commit the tag pointed at
- `source_date_epoch` — the value used during the build
- `rustc_version` / `cargo_version` — toolchain identity
- `container_image` — `fedora:43` for x86_64
- `glibc_version` / `kernel_uname` — host facts that influence the artifact
- `binary_sha256` — sha of the binary the manifest is talking about

Use this file to debug a mismatch. If your local rebuild produces a different hash, the most common cause is a different `rustc_version` or a different host glibc.

## Known sources of non-determinism (caveats)

These are tolerated by the current build pipeline; rebuilding outside the published recipe will produce a different hash:

- **glibc version**. The release artifact is dynamically linked against the glibc that ships with `fedora:43`. A rebuild on a host with a different glibc (Ubuntu LTS, Alpine via musl, an older Fedora) produces a different binary even with identical Rust source. The `.build-info` file records the glibc the release was built against; rebuild inside the same container to match.
- **Container layer digests**. We pin `fedora:43` and `ubuntu:24.04` by tag, not by digest. Docker Hub can re-tag those over time; the image digest at the moment of the release is recorded in the workflow logs but not in the build-info file. Pin to a specific digest if absolute reproducibility matters to you, and report drift if you find it.
- **Cross-compile linker**. The aarch64 binary is produced via `aarch64-linux-gnu-gcc` from `ubuntu-latest`; that linker version is captured in `cross_linker_version` in `.build-info` but is not pinned by digest.
- **Cargo's incremental cache**. Cargo's incremental compilation can introduce subtle order-of-build differences. `cargo build --release` with `codegen-units=1` (set in `Cargo.toml`) sidesteps most of this, and a fresh `target/` directory removes the rest. `verify-build.sh` always uses a fresh checkout, so this never bites.
- **Embedded wiki bytes**. The `wiki/` directory is embedded into the binary via `include_dir!`. Any byte change in any wiki page rolls the binary hash. That is a feature, not a bug — wiki edits are part of the source — but it means a "wiki-only" patch still requires a new release artifact.

## What this script does NOT verify

- **Wiki content**. The embedded wiki is part of the binary, so its bytes flow into the hash. There is no separate per-page diff. If you want to confirm a specific wiki page is what GitHub shows, read the page in `wiki/` at the tag's commit; the embedded copy is a verbatim include.
- **Release signatures**. The current release pipeline drafts a GitHub Release with `softprops/action-gh-release@v2`; the artifacts are not signed with a project key. Signing is on the roadmap but not part of this verification recipe.
- **Maintainer trust**. Reproducibility lets you confirm "the bytes match the source", not "the maintainer is honest". A maintainer who controls the source can ship malicious source, and reproducible builds will faithfully reproduce that. Read the source, or at least the diff against the previous tag, if that matters to you.
- **The toolchain itself**. We trust the pinned Rust toolchain that `rustup` installs. A compromised rustc would compromise every binary built with it. Bootstrapping rustc from source is out of scope.

## Building the workspace reproducibly

The repository is migrating to a Cargo workspace (roadmap 1.1). When the workspace layout lands, the build recipe is unchanged — `cargo build --release --frozen --locked` still runs from the workspace root and produces a single `proteus` binary. The difference is that Cargo now resolves two members (`proteus` and `crates/proteus-types`) in one pass, with a single `Cargo.lock` covering both.

What this means for reproducibility:

- **`--frozen --locked` applies workspace-wide.** Both members are built from the same `Cargo.lock`. There is no second lockfile for `proteus-types`.
- **`SOURCE_DATE_EPOCH` applies to both members.** `build.rs` in the root package and any `build.rs` in `crates/proteus-types` both pick up the epoch from the environment. The release workflow sets it once before invoking `cargo build`.
- **The pinned toolchain covers the whole workspace.** `rust-toolchain.toml` at the workspace root applies to every crate in the workspace. There is no per-crate toolchain override.
- **The JSON Schema is deterministic.** `proteus schema` bundles the schema as a static byte string generated at compile time (via `schemars`'s derive macro). Given the same `proteus-types` source and the same Rust toolchain, the schema bytes are identical across rebuilds. The schema bytes are part of the binary, so they flow into the `sha256sum` check automatically.

The `scripts/verify-build.sh` recipe is unchanged — clone, set epoch, build, strip, hash. The workspace layout is transparent to the script.

## JSON Schema in CI

CI runs `proteus schema` after a successful build and pipes the output through a schema validator to confirm the document is well-formed JSON Schema. Separately, the integration test suite runs `proteus <subcommand> --json` for every read command and validates the output against the matching `$defs` entry in the schema.

Two things CI catches:

1. **Schema regression**: if a DTO struct changes shape (a field removed, a type widened to `Option`, a new required field added) the schema changes, and the validator diff surfaces it. The PR author must either update the schema-version field or argue that the change is compatible.
2. **Output-schema drift**: if the binary's `--json` output no longer validates against the schema (a field added in the output but not in `proteus-types`, or vice versa), the integration test fails. This is the "schema is the contract" enforcement.

The CI step looks roughly like:

```sh
proteus schema > /tmp/proteus-schema.json
check-jsonschema --check /tmp/proteus-schema.json   # validates it is well-formed JSON Schema

proteus status --json > /tmp/status.json
# ajv supports per-definition validation via a JSON Pointer ref:
ajv validate -s /tmp/proteus-schema.json \
    -r /tmp/proteus-schema.json \
    --ref '#/$defs/StatusOutput' \
    -d /tmp/status.json
```

The exact tooling (`ajv`, `check-jsonschema`, or another validator) is a CI implementation detail; the invariant is that both checks must pass before the build is considered green.
